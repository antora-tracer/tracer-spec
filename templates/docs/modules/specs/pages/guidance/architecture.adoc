= Architecture Item

Use a traceable architecture item for an independently meaningful solution strategy, building block, runtime or deployment element, or cross-cutting concept. Keep explanatory prose and section headings in the arc42 baseline; do not turn every paragraph into a graph item.

The open `kind` metadata convention should describe the element consistently. Add typed links to requirements, related architecture items, decisions, and changes where they help explain structure or impact.

== Diagrams

Document each view with a diagram: a system context diagram in Context and Scope, a container or component diagram in the Building Block View, a sequence diagram in the Runtime View, a deployment diagram in the Deployment View, and a concept diagram in Crosscutting Concepts. Add a per-element diagram inside an ARC item's partial only when the element has internal structure worth drawing.

Write diagrams as text in a `[c4plantuml]`, `[plantuml]`, or `[mermaid]` block; the build renders them and embeds the result in the page. Each view in xref:architecture.adoc[Architecture] carries a commented slot showing where a diagram goes.

Keep each diagram's source in its own file under `docs/modules/specs/examples/diagrams/` and reference it from the view:

[source,asciidoc]
-----
[c4plantuml]
----
\include::example$diagrams/view-context.puml[]
----
-----

Name files on two axes: `view-<section>.puml` for a diagram that belongs to an arc42 section, and `<ARC-id>-<slug>.puml` for a diagram that describes one architecture item. A section may carry more than one diagram; give each its own file and its own include.

Do not write the notation and target as block attributes above a bare `include::`. A block such as `[c4plantuml, view-context, svg]` followed by `include::example$diagrams/view-context.puml[]` renders the source as a paragraph instead of a diagram. Put the include inside the delimited block, as shown above.

The default notation is C4, written with PlantUML's C4 includes (`C4_Context`, `C4_Container`, `C4_Component`). A project whose architecture is a component hierarchy MAY adopt traditional UML instead — class, component, sequence, and state diagrams — and SHOULD state that choice here.

Rendering runs during the documentation build through `asciidoctor-kroki`, registered in `antora-playbook.yml`.

== Item template

[source,asciidoc]
----
[#ARC-NNN, item, role=architecture, status=accepted, kind=<kind>, title="<specific element>"]
--
Summary:: What the element is and its purpose.
Description:: Relevant structure, responsibilities, or constraints.

composes:ARC-NNN[]
realizes:REQ-NNN[]
decided_by:ADR-NNN[]
updated_by:CHG-NNN[]
tracer:links[]
--
----
