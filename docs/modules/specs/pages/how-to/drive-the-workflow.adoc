= How to Drive the Workflow

Move from feature intent to one or more implemented changes. Refine product behavior from an existing feature ticket first; refine each implementation change before creating its tasks.

== 1. Explore the feature

[source,bash]
----
tspec-explore "Add user authentication"
----

Use `tspec-explore` to investigate the feature and shape its rationale, outcome, and scope. Exploration is read-only and creates no durable items.

== 2. Refine the feature ticket

[source,bash]
----
tspec-refine-feature <feature-ticket-id>
----

Start from an existing feature ticket when refining product behavior, use cases, and requirements; related graph items may share optional `externalId=<id>` metadata. One feature ticket may support many independent implementation changes. A local change can omit `externalId` when it addresses applicable approved requirements.

== 3. Record an implementation change

[source,bash]
----
tspec-new-change "Save review filters"
----

`tspec-new-change` records one change and its necessary decisions against applicable approved product/component requirements. `externalId` is optional; the skill does not author detailed software requirements or tasks. Repeat for each independent change, then refine each before creating its checklist.

== 4. Refine the change

[source,bash]
----
tspec-refine-change CHG-001
----

Refine the change into detailed software requirements, then create its execution checklist at `tspec/CHG-001/tasks.md`. Tasks are created only after this change-refinement step.
`tracer-spec status CHG-001` reports the stored lifecycle state and actionable/finished results without changing the graph.

== 5. Accept and apply the change

A human reviews the refined change and approves it before implementation. Validation enforces that an accepted change addresses at least one requirement.

[source,bash]
----
tspec-apply-change CHG-001
----

`tspec-apply-change` works through `tspec/CHG-001/tasks.md`, ticking each task and adding verification evidence for each addressed requirement. The change moves `accepted` → `implemented` → `verified`.

== 6. Archive the change

[source,bash]
----
tspec-archive CHG-001
----

`tspec-archive` validates, verifies conformance against the requirements with an independent cold reviewer, removes `tspec/CHG-001/`, and closes the change. Durable items remain in the graph; only the temporary checklist is removed.

== 7. Validate at any point

[source,bash]
----
tspec-validate
----

Validation checks roles, relations, statuses, and the acceptance gate. It runs at any time and never changes state.

== Read or update the feature ticket

`tspec-track` reads an existing ticket or, only with approval of the exact preview, updates its unique `TSPEC refinement` section:

[source,bash]
----
tspec-track --read <feature-ticket-id>
tspec-track --update-refinement <feature-ticket-id>
----

The update preserves all content outside that section (a GitHub or Forgejo Markdown heading, or the equivalent Jira ADF section). The user must approve the exact section preview before it is written. The external ticket remains authoritative for backlog position, status, and estimate; this workflow does not create or import tickets, or change those fields. Graph items may associate with the ticket through shared optional `externalId=<id>` metadata, not a relation.

== Write a single item

[source,bash]
----
tspec-write-item decision DEC-001
----

Use `tspec-write-item` to author one item of any declared role outside the propose/refine/apply cycle, wiring its relations directly.
