[#DEC-008, item, role=decision, status=proposed, title="Keep provider selection in tspec.yml without storing credentials"]
--
Context:: Feature-ticket refinement needs a provider selector to choose how to read an existing ticket and publish an explicitly approved summary. Credentials and ticket lifecycle state are owned by the user and provider tooling, not by the graph workflow.

Options::
* Put provider selectors, credentials, and ticket-status mappings in tracer-spec-owned `tspec.yml`.
** Good: the workflow controls the complete tracker integration.
** Bad: secrets and user-managed ticket lifecycle fields become project configuration.
* Keep `tspec.yml` as a thin selector for the user's GitHub, Jira, or Forgejo provider; credentials and ticket lifecycle state remain provider-owned.
** Good: TSPEC selects provider-specific ticket access without storing secrets or taking ownership of estimates, backlog, or status.
** Bad: ticket access depends on configured provider authentication.

Decision:: Keep `tspec.yml` as a thin selector for `none`, GitHub, Jira, or Forgejo; it contains provider choice only, not credentials, ticket-status mappings, or estimates.

Rationale:: The workflow needs provider-specific ticket access, while credentials and ticket state remain user/provider-owned. A selector supports the existing providers without storing secrets or taking over tracker lifecycle.

Consequences:: Scaffold `provider: none` by default. Use authenticated `gh` for GitHub, Jira Cloud REST with the user's existing `~/.netrc` host entry, and Forgejo's scoped issue API with `FORGEJO_TOKEN` from the process environment. Never place credentials in project config or command arguments. If authentication or safe body preservation fails, return a manual draft and do not write.
