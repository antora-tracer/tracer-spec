[#DEC-016, item, role=decision, status=proposed, title="Model architecture elements, change designs, and ADRs"]
--
Context:: The current decision role and a separate ADR role preserve choices, but do not make architecture elements or change-specific design traceable.

Options::
* Keep architecture descriptions as arc42 prose and add ADRs only.
** Good: smallest change to the current graph.
** Bad: architectural elements and change designs remain unlinked prose.
* Represent architectural elements and per-change design as traceable items, and retain ADRs for consequential choices.
** Good: requirements, change designs, architecture elements, and decisions can be traced together.
** Bad: adds roles, relations, and authoring guidance.

Decision:: Add one `architecture` role, classified with `kind` metadata, for independently meaningful elements organized in an arc42-aligned baseline.
Add one durable `design` item per refined change, linked to its requirements and affected architecture items.
Keep ADRs distinct for costly-to-reverse choices and `DEC` items for domain or business choices.

Rationale:: A system architecture model explains how the system is structured; per-change design explains how a change fits that model; ADRs preserve why a consequential option was chosen.

Consequences:: The traceability model and templates need architecture, design, and ADR roles, guidance, relations, and collection pages.
Each change's design remains after closure, and archive updates the architecture baseline to reflect the implemented system.
The accepted DEC-003 policy that design is recorded only as `decision` must be superseded when this change is implemented.
