[#DEC-011, item, role=decision, status=proposed, title="Separate feature and change refinement from ticket access"]
--
Context:: Product feature refinement, detailed change refinement, and provider-specific ticket access have different responsibilities. Combining them makes the change-proposal step author details prematurely and spreads provider behavior through lifecycle skills.

Options::
* Put all work in `tspec-propose` and `tspec-track`.
** Good: fewer workflow entry points.
** Bad: proposal authors detailed software requirements/tasks before change refinement; ticket logic becomes lifecycle logic.
* Separate feature refinement, change refinement, proposal, and tracker access.
** Good: `tspec-refine-feature` handles product-level feature definition; `tspec-propose` proposes changes without detailed software requirements/tasks; `tspec-refine-change` elaborates an approved change and creates tasks; `tspec-track` owns the limited external ticket interaction.
** Bad: requires using distinct workflow skills for distinct stages.

Decision:: Keep feature and change refinement separate, and centralize tracker access in `tspec-track`. Create tasks only after change refinement.

Rationale:: The workflow keeps product behavior, proposed change scope, detailed software requirements, and provider-specific interaction at their correct boundaries.

Consequences:: `tspec-track` reads an existing ticket via shared `featureTicketId` and, only after user approval, updates its unique `TSPEC refinement` section. It never creates/imports tickets, manages provider configuration, or writes status, backlog placement, or estimates.
