= Workflow Overview

== Phases

=== Explore

An idea or problem is identified.
The agent reads the code and weighs options without writing anything durable.
The output is a change sketch: rationale, intended outcome, and scope.

=== Propose

The change is written as a durable item, together with the requirements it addresses and the decisions it records.
A task checklist is written to `tspec/<change-id>/tasks.md`.
Status: `proposed`, then `refined` as the proposal is fleshed out.

=== Accept

A human reviews the proposal.
On the human's instruction the change advances from `refined` to `accepted`.
Validation enforces that an accepted change addresses at least one requirement.
Status: `accepted`

=== Apply

Tasks are implemented and ticked off in `tspec/<change-id>/tasks.md`.
Test evidence is added.
Status: `accepted` → `implemented` → `verified`

=== Archive

Validation runs, the `tspec/<change-id>/` directory is deleted, and the change closes.
Status: `verified` → `closed`

=== Validate

`antora-tracer validate` checks roles, relations, statuses, and matrices.
It runs at any time and does not change state.

== Status policy

States are declared in `traceability.yml`.
Validation enforces the acceptance gate and structural rules.
Git and pull requests provide review, authorization, and history.

== Change history

Git provides full history.
Graph snapshots may be generated at release boundaries for historical analysis.
