= Configuration Reference

Two configuration files drive the workflow, owned by different tools.
`antora-tracer` owns `traceability.yml`; `tracer-spec` owns `tspec.yml`.

== traceability.yml

The traceability model: roles, relations, matrices, workflow states, and validation.
It lives at the project root and is read by `antora-tracer` and every skill.

[source,yaml]
----
extends: minimal

roles:
  - change
  - decision
  - use_case
  - architecture
  - design
  - adr

roleGuidance:
  change:
    page: docs/modules/specs/pages/guidance/change.adoc
    idPrefix: CHG
  decision:
    page: docs/modules/specs/pages/guidance/decision.adoc
    idPrefix: DEC
  use_case:
    page: docs/modules/specs/pages/guidance/use-case.adoc
    idPrefix: UC
  architecture:
    page: docs/modules/specs/pages/guidance/architecture.adoc
    idPrefix: ARC
  design:
    page: docs/modules/specs/pages/guidance/design.adoc
    idPrefix: DSN
  adr:
    page: docs/modules/specs/pages/guidance/adr.adoc
    idPrefix: ADR

relations:
  change:
    requirement:
      addresses:
        reverse: addressed_by
    decision:
      records:
        reverse: recorded_by
    design:
      records:
        reverse: recorded_by
    adr:
      records:
        reverse: recorded_by
    architecture:
      updates:
        reverse: updated_by
    change:
      refines:
        reverse: refined_by
  use_case:
    requirement:
      leads_to:
        reverse: is_derived_from
  requirement:
    requirement:
      refines:
        reverse: refined_by
  design:
    requirement:
      realizes:
        reverse: realized_by
    architecture:
      affects:
        reverse: affected_by
    adr:
      references:
        reverse: referenced_by
  architecture:
    architecture:
      composes:
        reverse: part_of
    requirement:
      realizes:
        reverse: realized_by
  adr:
    requirement:
      addresses:
        reverse: addressed_by
    architecture:
      decides:
        reverse: decided_by
  decision:
    decision:
      supersedes:
        reverse: superseded_by

matrices:
  - name: changes-to-requirements
    rows: change
    columns: [requirement]
    coverageRelations:
      requirement: [addresses]
  - name: use-cases-to-requirements
    rows: use_case
    columns: [requirement]
    coverageRelations:
      requirement: [leads_to]
  - name: requirements-refinement
    rows: requirement
    columns: [requirement]
    coverageRelations:
      requirement: [refines]
  - name: architecture-to-requirements
    rows: architecture
    columns: [requirement]
    coverageRelations:
      requirement: [realizes]
  - name: designs-to-requirements
    rows: design
    columns: [requirement]
    coverageRelations:
      requirement: [realizes]

workflow:
  architecture:
    states: [accepted, superseded]
    transitions:
      accepted: [superseded]
  design:
    states: [proposed, accepted, superseded]
    transitions:
      proposed: [accepted, superseded]
      accepted: [superseded]
  decision:
    states: [proposed, accepted, rejected, superseded]
    transitions:
      proposed: [accepted, rejected, superseded]
      accepted: [superseded]
  adr:
    states: [proposed, accepted, rejected, superseded]
    transitions:
      proposed: [accepted, rejected, superseded]
      accepted: [superseded]
validation:
  change:
    accepted:
      requiresRoles: [requirement]
----

[cols="25a,75a"]
|===
| Key | Purpose

| `extends` | Base the model on a preset. `minimal` supplies `requirement` and `test`, their guidance, requirement workflow, requirement-test relations, and the `requirements-tests` matrix. These inherited roles, workflows, relations, and matrices remain available alongside project additions.
| `roles` | Additional roles declared by this project (`change`, `decision`, `use_case`, `architecture`, `design`, `adr`); they do not replace inherited `requirement` and `test` roles.
| `roleGuidance.<role>.page` | The page containing an item's role-specific template. `tspec-write-item` and refinement skills resolve it from `traceability.yml`.
| `roleGuidance.<role>.idPrefix` | The identifier prefix (`CHG`, `DEC`, `UC`, `ARC`, `DSN`, `ADR`; inherited roles use `REQ` and `TST`).
| `relations` | Typed edges between roles with reverse names. Changes record designs/decisions/ADRs and update architecture; designs realize requirements, affect ARC items, and reference ADRs; ADRs address requirements and decide architecture; architecture items compose and realize requirements.
| `matrices` | Cross-role coverage views. In addition to changes and use cases, architecture items and change designs are traceable to the requirements they realize; inherited `requirements-tests` remains.
| `workflow.<role>.states` | The ordered, declarative states a role may occupy; they do not enforce state transitions.
| `workflow.<role>.transitions` | Configured state-to-state moves, available to consumers as metadata.
| `validation` | Structural validation settings. Core does not enforce `requiresRoles` workflow gates.
|===

Use one `requirement` role for each abstraction level. `level=product`, `level=component`, and `level=software` are ordinary item metadata conventions, not separate roles or a core-validated enum.
Link a more detailed requirement to the broader requirement it refines with `refines`; behavior scenarios remain prose in requirement items, and verification evidence remains separate `test` items.


== tspec.yml

The `tracer-spec` selector for the user's issue-ticket provider.
It sits beside `traceability.yml` and is read by `tspec-track`; provider credentials and ticket state remain user-owned.

[source,yaml]
----
tracker:
  provider: none        # none | github | jira | forgejo

  # github:
  #   repo: owner/repo

  # jira:
  #   url: https://your-domain.atlassian.net
  #   project: KEY

  # forgejo:
  #   url: https://forgejo.example.org
  #   repo: owner/repo
----

[cols="25a,75a"]
|===
| Key | Purpose

| `tracker.provider` | The issue-ticket provider: `none` (default), `github`, `jira`, or `forgejo`. `none` disables external ticket access.
| `tracker.github.repo` | For `github`: the `owner/repo` reached by authenticated `gh`.
| `tracker.jira.url` | For Jira Cloud: the REST base URL; authenticate with the user's existing `~/.netrc` entry for that host.
| `tracker.jira.project` | For `jira`: the project key associated with feature tickets.
| `tracker.forgejo.url` | Forgejo instance base URL; the provider uses its `/api/v1` issue API.
| `tracker.forgejo.repo` | The single `owner/repo` whose issue indices are used for this project.
|===

External-item association is optional item metadata, not a `tspec.yml` setting: related canonical graph items may share `externalId=<id>`. It is not a graph relation; one external item may be associated with multiple independent changes.

Forgejo also requires `FORGEJO_TOKEN` in the process environment, with `read:issue` for reads and `write:issue` for approved updates. Never store the token in `tspec.yml`.

`tspec-track --read <feature-ticket-id>` reads an existing ticket. `tspec-track --update-refinement <feature-ticket-id>` replaces only the unique `TSPEC refinement` section after the user approves the exact preview; content outside that section is preserved. The ticket is authoritative for backlog position, status, and estimate. The bridge does not create or import tickets or write those fields.
