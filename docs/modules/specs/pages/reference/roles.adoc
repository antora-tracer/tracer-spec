= Roles Reference

Every traceability item has a role, ID prefix, item fields, and status conventions; architecture items also use open `kind` metadata.
This page is the authoritative reference for authoring items.

== Roles and prefixes

[cols="20a,15a,25a,40a"]
|===
| Role | Prefix | Initial status | Purpose

| `change` | `CHG` | `proposed` | The entry point: rationale, outcome, and scope of one change.
| `requirement` | `REQ` | `draft` | One observable obligation at product, component, or software level.
| `use_case` | `UC` | — | An actor goal and observable interaction leading to requirements.
| `decision` | `DEC` | `proposed` | A durable domain or specification choice.
| `architecture` | `ARC` | `accepted` | An independently meaningful system architecture element classified by `kind`.
| `design` | `DSN` | `proposed` | The durable technical design for one implementation change.
| `adr` | `ADR` | `proposed` | A decision record for a costly-to-reverse software architecture choice.
| `test` | `TST` | — | Verification evidence carrying `verifies:REQ-NNN[]`.

|===

Other growth roles are available only when declared in `traceability.yml`. The `minimal` preset supplies the inherited `requirement` and `test` roles, requirement workflow, requirement relations, and `requirements-tests` matrix. This project adds `change`, `decision`, `use_case`, `architecture`, `design`, and `adr`; inherited roles and coverage remain.

== Requirements

A requirement states what the system must do — never how.

Use EARS patterns:

* *Ubiquitous:* `The system SHALL <behaviour>.`
* *Event-driven:* `WHEN <trigger>, the system SHALL <behaviour>.`
* *State-driven:* `WHILE <state>, the system SHALL <behaviour>.`
* *Unwanted behaviour:* `IF <condition>, THEN the system SHALL <behaviour>.`

Scenarios stay as prose inside the requirement body.

A requirement may carry exactly one project convention for `level`: `product`, `component`, or `software`.
These values are ordinary item metadata, not separate roles or a core-validated enum.
Use the same `requirement` role at every level; a more detailed requirement points to the broader one with `refines:REQ-NNN[]`.
Behavior scenarios, including BDD-style examples, remain prose in requirement items; tests remain separate `test` items linked with `verifies`.

== Requirement item shape

Use role `requirement` with item metadata `level=product`, `level=component`, or `level=software`.
Keep one observable obligation in the body; a more detailed requirement carries a configured refinement relation to its broader requirement.
These levels are metadata conventions, not separate roles.

== Use-case item shape

Use role `use_case` with a `UC`-prefixed ID and a table describing a specific actor, goal, trigger, preconditions, observable flows, postconditions, priority, and frequency.
Add the configured use-case-to-requirement relation when a relevant requirement exists.

== Changes

A change is the entry point.
It carries `Rationale::`, `Outcome::`, and `Out-of-scope::` fields and links addressed requirements, its durable design, recorded decisions/ADRs, and updated architecture items.

== Decisions

A decision preserves a domain or specification choice.
Decisions may additionally carry `Options::` (per-option pros and cons) and `Rationale::` fields, following the MADR shape documented in xref:guidance/decision.adoc[the decision guidance].
Costly-to-reverse software architecture choices are recorded as ADRs; domain and business choices remain `decision` items.

== Architecture items

Use role `architecture` for independently meaningful elements such as solution strategies, building blocks, runtime or deployment elements, and cross-cutting concepts.
Classify each with the open `kind` metadata convention and organize the items under the relevant sections of the arc42 baseline.
Arc42 headings and explanatory prose remain documentation, not graph items by default.

== Change designs

Use one durable `design` item for each refined change.
Create it after software requirements and before temporary tasks.
Link it to the change, requirements it realizes, affected architecture items, and related ADRs.
Keep it after the change closes; archive removes only the temporary checklist.

== Architecture Decision Records

Use `adr` only for costly-to-reverse software architecture choices.
An ADR captures context, options, decision, rationale, and consequences, and links to its change, relevant requirements, and affected architecture items.
Domain and business choices remain `decision` items.


== Relation macros

A relation macro `<relation>:<ID>[]` is written in the source item.
The configured reverse name is available for queries and may be authored where listed.

[width=100%, cols="30a,30a,20a,20a"]
|===
| Source → Target | Macro | Reverse | Used in
| use_case → requirement | `leads_to:REQ-NNN[]` | `is_derived_from` | use_case
| requirement → requirement | `refines:REQ-NNN[]` | `refined_by` | requirement
| change → requirement | `addresses:REQ-NNN[]` | `addressed_by` | change
| change → decision | `records:DEC-NNN[]` | `recorded_by` | change
| change → design | `records:DSN-NNN[]` | `recorded_by` | change
| change → adr | `records:ADR-NNN[]` | `recorded_by` | change
| change → architecture | `updates:ARC-NNN[]` | `updated_by` | change
| design → requirement | `realizes:REQ-NNN[]` | `realized_by` | design
| design → architecture | `affects:ARC-NNN[]` | `affected_by` | design
| design → adr | `references:ADR-NNN[]` | `referenced_by` | design
| architecture → architecture | `composes:ARC-NNN[]` | `part_of` | architecture
| architecture → requirement | `realizes:REQ-NNN[]` | `realized_by` | architecture
| adr → requirement | `addresses:REQ-NNN[]` | `addressed_by` | adr
| adr → architecture | `decides:ARC-NNN[]` | `decided_by` | adr
| decision → decision | `supersedes:DEC-NNN[]` | `superseded_by` | decision
| requirement → requirement | `depends_on:REQ-NNN[]` | `is_prerequisite_of` | requirement
| requirement → requirement | `supersedes:REQ-OLD[]` | `superseded_by` | requirement
| test → requirement | `verifies:REQ-NNN[]` | `verified_by` | test
|===

== Workflow states

Use the `status` attribute to mark progression.

[width=100%, cols="20h,80a"]
|===
| Role | States or status convention
| requirement | `draft` → `reviewed` → `approved` → `superseded` · `withdrawn`
| test | No configured lifecycle states
| change | `proposed` → `refined` → `accepted` → `implemented` → `verified` → `closed` · `rejected`
| decision, adr | `proposed` → `accepted` → `rejected` · `superseded`
| architecture | `accepted` current element · `superseded` historical element
| design | `proposed` → `accepted` · `superseded`
|===

The `accepted` gate is enforced by validation: an accepted change must address at least one requirement.
Other transitions are declarative and reviewed via Git.
