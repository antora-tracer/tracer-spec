= Skills Reference

The Tracer Spec Workflow ships nine skills.
Each is a self-contained instruction file; this page catalogs every skill's trigger, argument, and tool access.
The `SKILL.md` files are the source of truth — this page mirrors their frontmatter.

[width=100%, cols="20a,45a,15a,20a"]
|===
| Skill | Purpose | Argument | Tools

| `tspec-explore` | Explore a feature idea and shape its change sketch. | `<topic>` | unrestricted (read-only)
| `tspec-refine-feature` | Refine an existing feature ticket into product-level graph items. | `<feature-ticket-id>` | `antora-tracer`, tracker CLI/API
| `tspec-new-change` | Record a context-first implementation change against approved requirements. | `<change idea>` | `antora-tracer`
| `tspec-refine-change` | Refine a proposed change into detailed software requirements and tasks. | `<change-id>` | `antora-tracer`
| `tspec-apply-change` | Implement a change's tasks and advance state. | `<change-id>` | `antora-tracer`
| `tspec-archive` | Validate, verify, and close a change. | `<change-id>` | `antora-tracer`
| `tspec-validate` | Validate the traceability graph. | — | `antora-tracer`
| `tspec-write-item` | Write one item of any role. | `<role> [<id>]` | `antora-tracer`
| `tspec-track` | Read or update an existing feature ticket. | `--read` or `--update-refinement` with `<feature-ticket-id>` | `antora-tracer`, `gh`, `curl`, `node`
|===

== Skill evaluation suite

Evaluation suites are JSON files at `skills/<skill>/evals/evals.json`.
Each suite contains a matching `skill_name` and a non-empty `evals` array.
Each evaluation has a numeric `id`, `name`, task `prompt`, repository-relative fixture directory, optional `expected_output`, and `expectations` array.

Each expectation has a description in `text`, a supported `type`, and an optional `configuration` selector (`with_skill`, `without_skill`, or `both`).
If the selector is omitted, the check runs against both configurations.

[cols="30a,70a"]
|===
| Type | Result

| `assistant_contains`, `assistant_not_contains` | Check the final assistant response for a literal substring.
| `transcript_contains` | Check the complete CLI transcript for a literal substring.
| `workspace_unchanged` | Require no fixture-file changes.
| `workspace_changed_under` | Require at least one fixture-file change under the relative `path`.
| `file_exists`, `file_not_exists` | Check the relative `path` in the fixture.
| `file_contains` | Find literal `value` in the file at the relative `path`.
| `directory_contains` | Find literal `value` in any file below the relative `path`.
| `new_file_contains` | Find literal `value` in any newly created or modified file below the relative `path`.
| `exit_code` | Compare `value` with the Claude CLI process exit code.
|===

File checks reject absolute paths and paths that escape the fixture.
Expectations are deterministic checks, not a measure of reasoning quality.

== tspec-explore

Enter explore mode — a thinking partner that produces a change sketch (rationale, outcome, scope) without writing durable content.
Read-only by discipline: it may read files, search code, and run commands, but must not edit the repo or `docs/modules/specs/pages/`.

== tspec-refine-feature

Refine an existing feature ticket into product-level behavior, use cases, and requirements. Related canonical graph items may carry shared scalar metadata `externalId=<id>`; one ticket may be associated with many independent changes. The ticket remains authoritative for backlog position, status, and estimate.

== tspec-new-change

Record one proposed implementation change from conversation context and existing approved product/component requirements. `externalId` is optional; local changes still require applicable approved requirement links. The skill previews the item before writing, generates the ID, resolves role guidance, adds the collection include, and validates. It does not author detailed software requirements or tasks.


== tspec-refine-change

Refine a proposed change into detailed software requirements and an execution task checklist at `tspec/<change-id>/tasks.md`. Tasks are created only after the change is refined.

== tspec-apply-change

Implement an accepted change: work the task checklist, tick `- [ ]` to `- [x]`, add verification evidence for each addressed requirement, and advance `accepted` → `implemented` → `verified`.
Never modifies requirements in place — a changed meaning is a supersession.

== tspec-archive

Close a verified change: validate, spawn an independent cold reviewer that verdicts each requirement SATISFIED/NOT, then delete `tspec/<change-id>/` and advance `verified` → `closed`.
Stops on any NOT-satisfied verdict.

== tspec-validate

Run `antora-tracer validate` and report the summary plus any errors with file and line.
Never changes state.

== tspec-write-item

Write one item of any declared role (`change`, `requirement`, `decision`, `test`, or a declared growth role) and wire its relations directly.
Generates the next ID from the role's prefix and writes into the role's page.

== tspec-track

Read an existing feature ticket or update its approved refinement section.

[cols="25a,75a"]
|===
| Operation | Behavior

| `--read <feature-ticket-id>` | Read an existing linked GitHub or Jira feature ticket; it does not change the graph or ticket.
| `--update-refinement <feature-ticket-id>` | After the user approves the exact preview, replace only the ticket's unique `TSPEC refinement` section (GitHub heading or equivalent Jira ADF section), preserving the rest of the ticket.
|===

The ticket must already exist; this skill does not create or import tickets, change ticket status or backlog position, or own estimates. The external ticket remains authoritative for those fields. Related graph items may share optional `externalId=<id>` metadata; it is not a graph relation. Existing unknown legacy `trackerId` data is preserved and is not converted automatically.

Configuration lives in `tspec.yml` under `tracker`.
`provider: none` (the default) disables external ticket operations; `github` uses the `gh` CLI and `jira` uses REST against the configured `url` and `project`.
The tracker bridge reads existing tickets and writes only a user-approved refinement section; it never synchronizes tracker status or estimates.
