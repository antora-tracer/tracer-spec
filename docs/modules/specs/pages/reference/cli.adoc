= CLI Reference

include::partial$documentation/DOC-004-cli-reference.adoc[]

This page documents every command and option of the Tracer Spec Workflow CLI.
The traceability model itself is the `antora-tracer` CLI, covered for the commands the workflow uses.

== tspec

`tspec` scaffolds a project and installs the workflow skills.
It ships three commands: `init`, `install`, and `status`.

=== init

Initialize a Tracer Spec Workflow project in the current directory.

[source,bash]
----
tspec init [name] [options]
----

[cols="30a,70a"]
|===
| Argument | Description

| `name` | Project name, also used as the Antora component name and site title.
Defaults to the current directory name.
|===

[cols="25a,75a"]
|===
| Option | Description

| `--force` | Overwrite existing files instead of skipping them, including scaffold files.
Existing symlinks are replaced rather than written through.

| `--skip-skills` | Do not install the workflow skills, slash commands, or agent definitions into any harness.
Installs nothing, regardless of `--tools`.

| `--link` | Install skills and agent definitions as symlinks to the package's sources instead of copies.
Run the CLI from a repository checkout to link to working-tree files; a globally installed CLI links to its installed package.
Slash commands are always copies.

| `--scope <scope>` | Select `project` or `user` installation.
When omitted in a terminal, prompts with `project` selected; without a TTY, defaults to `project`.
This option changes skill and agent destinations; scaffolding and slash commands remain project-local.

| `--dry-run` | Preview actions without writing any file.
Prints the component name, title, selected harnesses, and every file that would be created.

| `--tools <ids>` | Agent harnesses to install for: a comma-separated list, `all`, or `none`.
When omitted and the terminal is interactive, shows a picker; when not a terminal, defaults to `oh-my-pi,claude,agents`.
|===

==== Harnesses

[width=100%, cols="20a,20a,30a,30a"]
|===
| ID | Label | Project skill directory | User skill directory

| `oh-my-pi` | Oh My Pi | `.omp/skills` | `~/.omp/agent/skills`
| `claude` | Claude Code | `.claude/skills` | `~/.claude/skills`
| `codex` | Codex | `.agents/skills` | `~/.agents/skills`
| `pi` | Pi | `.pi/skills` | `~/.agents/skills`
| `agents` | Shared .agents | `.agents/skills` | `~/.agents/skills`
|===

`omp` is an alias for `oh-my-pi`.
`codex` and `agents` share `.agents/skills` at project scope; `codex`, `pi`, and `agents` share `~/.agents/skills` at user scope.

Slash commands are installed only for harnesses that define a command convention: Oh My Pi (`.omp/commands/tspec-<id>.md`) and Claude Code (`.claude/commands/tspec/<id>.md`).
Slash commands remain project-local for either skill installation scope.

==== Agents

Harnesses that declare an agent convention also receive the shipped agent definitions.
Each agent is installed in its harness's own format and directory.

[width=100%, cols="20a,25a,27a,28a"]
|===
| ID | Project agent directory | User agent directory | Format

| `oh-my-pi` | `.omp/agents` | `~/.omp/agent/agents` | Markdown with YAML frontmatter
| `claude` | `.claude/agents` | `~/.claude/agents` | Markdown with YAML frontmatter
| `codex` | `.codex/agents` | `~/.codex/agents` | TOML
|===

Pi and the shared `.agents` directory have no agent convention and install skills only.
Shipped agents are named with a `tspec-` prefix so they never replace a harness's own or bundled agent.
The shipped conformance reviewer is read-only by tool list on Oh My Pi and Claude Code; Codex offers no per-agent write toggle, so read-only there rests on the agent's instructions.

=== install

Install the workflow skills, slash commands, and agent definitions into the selected harnesses without writing any scaffold file.
Run it from an existing project root to refresh harness files while leaving project content untouched.

[source,bash]
----
tspec install [options]
----

[cols="25a,75a"]
|===
| Option | Description

| `--force` | Overwrite existing harness files instead of skipping them.
Existing symlinks are replaced rather than written through.

| `--link` | Install skills and agent definitions as symlinks to the package's sources instead of copies.
Run the CLI from a repository checkout to link to working-tree files.
Slash commands are always copies.

| `--scope <scope>` | Select `project` or `user` installation.
When omitted in a terminal, prompts with `project` selected; without a TTY, defaults to `project`.

| `--dry-run` | Preview actions without writing any file.
Prints the selected harnesses and every harness file that would be created.

| `--tools <ids>` | Agent harnesses to install for: a comma-separated list, `all`, or `none`.
When omitted and the terminal is interactive, shows a picker; when not a terminal, defaults to `oh-my-pi,claude,agents`.
Passing `none`, or leaving no harness selected, exits nonzero and writes nothing.
|===

Unlike `init`, `install` never scaffolds: it writes no `traceability.yml`, `docs/`, `AGENTS.md`, or other project file.
With `--force` it refreshes harness files without overwriting project content.

=== status

Report the lifecycle and derived readiness of one change. Run from a Tracer Spec project root.

[source,bash]
----
tspec status <change-id> [options]
----

[cols="25a,75a"]
|===
| Option | Description

| `-c, --config <path>` | Traceability configuration file. Defaults to `traceability.yml`.
| `--docs <path>` | AsciiDoc source directory. Defaults to `docs/`.
|===

Both paths resolve independently relative to the command's current working directory. When running outside the project root, pass both paths.

The command reads the selected configuration and AsciiDoc source paths and prints one line containing only the change ID, its stored lifecycle status, and `actionable` and `finished` results. It never writes graph or task files or contacts a tracker.

A leaf is actionable when its status is `refined` or `accepted`; it is finished only when `closed`. A closed or rejected parent is not actionable. An unclosed parent is actionable when every child linked through `refines:CHG-parent[]` is actionable; this is evaluated recursively. Any cycle in change refinement links, duplicate item IDs in the scanned graph, or an ID that does not resolve to a change exit nonzero with an error and no status line.

=== check

Check one change against a rule the graph alone cannot decide. Run from a Tracer Spec project root.

[source,bash]
----
tspec check <change-id> [options]
----

[cols="25a,75a"]
|===
| Option | Description

| `-c, --config <path>` | Traceability configuration file. Defaults to `traceability.yml`.
| `--docs <path>` | AsciiDoc source directory. Defaults to `docs/`.
|===

The command answers whether a change that has a temporary task checklist at `tspec/<change-id>/tasks.md` also has a durable design item recording it in the graph. Execution tasks are files rather than graph items — `validate` never sees them — so a rule about their ordering spans the filesystem and the graph and needs a command that reads both.

[cols="30a,70a"]
|===
| Output | Meaning

| `<id> check=ok design=DSN-NNN` | The change has a task checklist and the graph records its design. Exits zero.
| `<id> check=skipped (...)` | The change has no task checklist, so the rule does not apply. Exits zero.
| `Error: <id> has tspec/<id>/tasks.md but the graph records no design item` | The checklist exists with no recorded design. Exits nonzero.
|===

A design is recorded through the authorable `records:DSN-NNN[]` relation on the change; the design's `recorded_by` is the derived name and is not authored. The command is read-only: it reports a missing design rather than creating one.

=== coverage

Report how many current requirements a test item verifies. Run from a Tracer Spec project root.

[source,bash]
----
tspec coverage [options]
----

[cols="25a,75a"]
|===
| Option | Description

| `-c, --config <path>` | Traceability configuration file. Defaults to `traceability.yml`.
| `--docs <path>` | AsciiDoc source directory. Defaults to `docs/`.
| `--list` | Also print every uncovered requirement ID, one per line.
|===

[source,text]
----
requirements=107 covered=46 uncovered=61 coverage=43.0%
----

A test declares `verifies:REQ-NNN[]`, which the graph stores with the requirement as source, so coverage counts requirements whose own relationships carry a test link. Superseded requirements are excluded from `requirements` and from `uncovered`: a requirement kept only for audit is not expected to have a test. The figure matches the site's `requirements-tests` matrix.

Use it before proposing a change, to see which requirements already have verification and which are open, and to decide whether a new requirement needs a test alongside it.

== antora-tracer

`antora-tracer` is the graph engine behind the workflow.
The workflow uses these commands directly.

[cols="30a,70a"]
|===
| Command | Purpose

| `validate -i docs --config traceability.yml` | Check roles, relations, statuses, and the acceptance gate.
| `next-id --prefix CHG -i docs` | Return the next unused ID for a role prefix.
| `role-guidance <role> --config traceability.yml --content` | Print a role's item template and prefix, resolved from `traceability.yml`.
|===

The full `antora-tracer` CLI is documented in its own reference; this workflow depends on it as `@antora-tracer/core`.
See xref:reference/validation.adoc[Validation Reference] for what `validate` checks, refuses, and does not enforce.
== Skill evaluation

`npm run eval:skills --` runs one skill's scenario suite with Claude Code.
Each scenario runs once with the skill and once with skill commands disabled, against separate copies of the same fixture.

[source,bash]
----
npm run eval:skills -- --skill <name> [options]
----

Options:

`--skill <name>` is required and names a directory under `skills/` containing `SKILL.md`.
`--scenario <file>` selects an evaluation suite; the default is `skills/<name>/evals/evals.json`.
`--output <dir>` selects the report directory; the default is `eval-results/<name>-<timestamp>/`.
`--model <id>` selects the Claude model; the default is the CLI-configured model.
`--claude <executable>` selects the Claude Code executable; the default is `claude` on `PATH`.

The report contains per-run transcripts, standard error, workspace-change summaries, deterministic expectation evidence, execution durations, model metadata, and aggregate JSON and Markdown summaries.
The fixture directories must be trusted: the runner is not a security sandbox and does not prevent external side effects.
