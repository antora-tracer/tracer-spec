= Architecture Item

An *Architecture item* represents one independently meaningful element of the system architecture, not an entire arc42 section or an explanatory paragraph.

Use stable `ARC` identifiers for solution strategies, building blocks, runtime or deployment elements, cross-cutting concepts, quality scenarios, risks, and glossary terms when they need links or change-impact history.

The `kind` attribute classifies the element. Use concise, consistent values such as `solution_strategy`, `building_block`, `runtime_scenario`, `deployment_element`, and `crosscutting_concept`; other specific values are valid when needed.

The arc42 baseline in xref:architecture.adoc[Architecture] groups these items by section. Keep supporting prose in that page and link each item to the requirements, other architecture items, decisions, or changes it affects.

== Diagrams

Document each view with a diagram: a system context diagram in Context and Scope, a container or component diagram in the Building Block View, a sequence diagram in the Runtime View, a deployment diagram in the Deployment View, and a concept diagram in Crosscutting Concepts. Add a per-element diagram inside an ARC item's partial only when the element has internal structure worth drawing.

Write diagrams as text in a `[c4plantuml]`, `[plantuml]`, or `[mermaid]` block; the build renders them and embeds the result in the page.

=== Diagram source files

Keep each diagram's source in its own file under `docs/modules/specs/examples/diagrams/` and reference it from the view:

[source,asciidoc]
-----
[c4plantuml]
----
\include::example$diagrams/view-context.puml[]
----
-----

Name files on three axes: `view-<section>.puml` for a diagram that belongs to an arc42 section, `<ARC-id>-<slug>.puml` for a diagram that describes one architecture item, and `<DSN-id>-<slug>.puml` for a diagram that explains one change design. A section may carry more than one diagram; give each its own file and its own include.

Do not write the notation and target as block attributes above a bare `include::`. A block such as `[c4plantuml, view-context, svg]` followed by `include::example$diagrams/view-context.puml[]` renders the source as a paragraph instead of a diagram. Put the include inside the delimited block, as shown above.

When an example must not be live, escape the macro according to its kind. `include::` is a block macro, so backticks are enough: `` `include::partial$<role>/<file>.adoc[]` `` stays inert. `xref:` is an inline macro and is preprocessed even inside backticks, so it needs a backslash: `` `\xref:requirements.adoc#REQ-NNN[REQ-NNN]` ``. An unescaped `xref:` in a template renders as a link to an anchor that does not exist.

=== Notation

The default notation is C4, written with PlantUML's C4 includes (`C4_Context`, `C4_Container`, `C4_Component`). C4 maps directly onto the arc42 views.

A project whose architecture is a component hierarchy MAY adopt traditional UML instead — class, component, sequence, and state diagrams — and SHOULD state that choice here. The choice is a convention this guidance records; the graph carries no notation field.

=== Rendering

Rendering runs during the documentation build through `asciidoctor-kroki`, configured in `antora-playbook.yml`; see xref:reference/config.adoc[Configuration Reference] for the rendering attributes. With `kroki-fetch-diagram: true` the build fetches each rendered diagram and embeds it, so a reader needs no network access; an unreachable service skips the block, the page falls back to the diagram source with a warning, and the build still exits 0.

== Item template

[source,asciidoc]
----
[#ARC-NNN, item, role=architecture, status=accepted, kind=<kind>, title="<specific element>"]
--
Summary:: What the element is and its architectural purpose.
Description:: The relevant structure, responsibilities, or constraints.

composes:ARC-NNN[]
realizes:REQ-NNN[]
decided_by:ADR-NNN[]
updated_by:CHG-NNN[]
tracer:links[]
--
----

Use only the relation macros relevant to the item.
