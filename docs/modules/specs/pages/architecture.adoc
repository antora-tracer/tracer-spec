= Architecture
:traceability-links: true

This is a tailored arc42 baseline for the Tracer Spec Workflow. The headings organize the system description; stable architectural elements are separate `ARC` items linked from the relevant sections. Keep only useful detail here and avoid duplicating requirements or decision records.

== 1. Introduction and Goals

Tracer Spec provides a requirement-anchored workflow for proposing, refining, implementing, and verifying changes. The product outcome is captured in xref:requirements.adoc#REQ-051[REQ-051].

== 2. Constraints

The canonical graph is stored as AsciiDoc items under `docs/modules/specs/pages/` and validated by `antora-tracer`. `traceability.yml` declares project roles and relations; the project extends the `minimal` preset rather than defining a separate graph format.

== 3. Context and Scope

Project contributors and coding agents use the TSPEC skills. `antora-tracer` parses and validates the graph; Antora publishes its pages. Optional issue-tracker access is isolated in `tspec-track`; the tracker remains authoritative for ticket state and estimates.

== 6. Runtime View

The normal change flow is `tspec-explore` → `tspec-refine-feature` → `tspec-new-change` → `tspec-refine-change` → `tspec-apply-change` → `tspec-archive`. Refinement produces durable requirements and a design item before the temporary task list; apply and archive preserve the graph as the system changes.

== 7. Deployment View

The repository contains the Antora source and the scaffolding templates. `tspec init` copies templates into a project and installs the selected workflow skills, slash commands, and agent definitions into the assistant's harness directories; `tspec install` installs those harness files alone, without scaffolding, so an existing project can refresh them. Harnesses with a declared agent convention receive skills and agents in their own directory and format; the rest receive skills only. Antora publishes the documentation site from those pages.

== 9. Architecture Decisions

Costly-to-reverse software architecture choices are recorded as ADR items on xref:adrs.adoc[Architecture Decisions]. Domain and workflow choices remain in xref:decisions.adoc[Decisions].

== 10. Quality Requirements

Quality requirements are `role=requirement` items like any other; the ISO 25010 characteristic is noted per group.
Human review gates, requirement links, and graph validation are central quality properties. See approved xref:requirements.adoc#REQ-083[REQ-083] and xref:requirements.adoc#REQ-051[REQ-051].

=== Security

_ISO 25010: Security — degree to which a product protects information so that persons have the degree of data access appropriate to their types and levels of authorization._

* xref:requirements.adoc#REQ-121[REQ-121] — Keep tracker credentials out of the repository and command text
* xref:requirements.adoc#REQ-122[REQ-122] — Reject a tracker URL that carries credentials or is not HTTPS

=== Reliability

_ISO 25010: Reliability — degree to which a system performs specified functions under specified conditions for a specified period._

* xref:requirements.adoc#REQ-125[REQ-125] — Report a malformed configuration with a nonzero exit and its location

=== Performance Efficiency

_ISO 25010: Performance Efficiency — performance relative to the amount of resources used._

* xref:requirements.adoc#REQ-126[REQ-126] — Validate a thousand-item graph within one second

=== Safety

_ISO 25010: Safety — degree to which a product under defined conditions avoids a state in which human life, health, property, or the environment is endangered._

* xref:requirements.adoc#REQ-123[REQ-123] — Write nothing outside the selected harness directories, even with force

=== Maintainability

_ISO 25010: Maintainability — degree of effectiveness and efficiency with which a product or system can be modified._

* xref:requirements.adoc#REQ-069[REQ-069] — State one obligation per requirement
* xref:requirements.adoc#REQ-023[REQ-023] — Assign each site page to exactly one Diátaxis mode

=== Gap

No requirement yet covers usability (error-message quality, discoverability) or flexibility (extensibility, configurability).
These groups are absent rather than satisfied; record them when a concrete need is stated.

== 11. Risks and Technical Debt

The traceability configuration, role guidance, skill instructions, and starter templates can drift apart. The graph validator checks configured item links; site builds and workflow smoke checks cover the published guidance and authoring path.

Duplicate item IDs are a live defect in the `antora-tracer` parser, not in this project's graph: it keeps the first block and silently discards the rest, so validation reports success on a graph that lost items. Fixing it belongs upstream; tracked as https://github.com/rattermeyer/antora-tracer/issues/18[antora-tracer#18].

REQ-084 is approved but unsatisfied. It requires validation to enforce the accepted-state transition, and `validation.change.accepted.requiresRoles` is declared in this project's `traceability.yml` and read by nothing: an accepted change that addresses no requirement exits zero. The `spec-driven-development` preset advertises the same key, so the defect is in the validator rather than in either configuration, and no configuration edit can close it. Tracked as https://github.com/rattermeyer/antora-tracer/issues/22[antora-tracer#22]; the alternatives are for upstream to enforce the key or to remove it.
