= How Traceability Works

include::partial$documentation/DOC-014-how-traceability-works.adoc[]

This page explains how items and their relations become the matrices, coverage reports, and self-tracing site.

== Items carry relations in their source

An item is an AsciiDoc block with an ID, a role, and a status:

[source,asciidoc]
----
[#CHG-010, item, role=change, status=proposed, title="..."]
--
addresses:REQ-021[]
records:DEC-013[]
tracer:links[]
--
----

The relation macros (`addresses:`, `records:`, `verifies:`, `supersedes:`) are written in the source item.
The reverse name is derived for queries, so `addresses` from a change is `addressed_by` from a requirement's perspective.

== The graph is parsed, not stored separately

`antora-tracer` reads the item blocks from the AsciiDoc pages and builds the graph from the role attributes and relation macros.
There is no separate database: the documentation *is* the model.

== Matrices and coverage

A matrix in `traceability.yml` declares which relation counts as coverage:

[source,yaml]
----
matrices:
  - name: changes-to-requirements
    rows: change
    columns: [requirement]
    coverageRelations:
      requirement: [addresses]
----

The site renders this as a matrix showing each change against the requirements it addresses, and a coverage report that flags requirements with no addressing change and changes with no addressed requirement.

== The published graph

Beyond the rendered pages, the build publishes the graph itself as data under xref:attachment$traceability/overview.html[Traceability overview] and xref:attachment$traceability/graph.json[Graph snapshot (JSON)], both reachable from the Traceability section of the contents list.

The JSON snapshot is the same graph the site renders, as a machine-readable document:

[source,json]
----
{
  "format": 1,
  "component": "tracer-spec",
  "version": "",
  "items": [
    { "id": "REQ-009", "title": "REQ-009 — Decision guidance declares an item template",
      "role": "requirement", "status": "superseded", "content": "…",
      "tags": [], "attributes": { "level": "component" },
      "sourceFile": "…", "sourceLine": 194, "module": "specs" }
  ],
  "relationships": [
    { "id": "REQ-013-supersedes-REQ-009", "fromId": "REQ-013", "targetId": "REQ-009",
      "type": "supersedes", "sourceFile": "…", "line": 12, "component": "tracer-spec",
      "fromIdentity": "…", "targetIdentity": "…", "autoGenerated": false }
  ]
}
----

`items` and `relationships` carry the relations the item bodies declare, with a `role` and `status` per item and a `type` per relationship, so a consumer can answer coverage, impact, or supersession questions without parsing AsciiDoc. Each item also carries the `attributes` that were authored on it, which is where an item's own metadata such as a requirement's `level` or an architecture item's `kind` lives.

Every published page is re-derived from this graph, so the snapshot and the rendered site cannot disagree.

The `format` value is the schema version; a consumer should reject a snapshot whose `format` it does not know rather than guessing at the fields.

== Self-traceability

This site traces itself.
Its own changes, requirements, decisions, and tests are the items in the graph, and the pages under `changes/`, `requirements/`, `decisions/`, and `tests/` render those items alongside the matrices and coverage reports.
Test items carry `verifies:` relations that record evidence for requirements implemented by a change.

The extension that produces the graph is the same extension this documentation describes — the site demonstrates the workflow it teaches.
