= Why the Workflow Works This Way

The Tracer Spec Workflow connects product intent from an existing feature ticket to one or more independently delivered implementation changes. This page explains why product refinement, change refinement, and ticket tracking are separate.

== The graph is the source of truth for the specification

Traditional spec workflows keep changes, requirements, and decisions in separate documents that drift apart. Here they are items in one graph: a change addresses requirements and records decisions, and those typed relations are queryable and renderable.

Git and pull requests provide review, authorization, and history; the graph provides the specification structure. Neither replaces the other. The external feature ticket remains authoritative for backlog position, ticket status, and estimate.

== From feature to changes

[source,text]
----
explore → refine feature → record change(s) → refine each change → accept → apply → archive
----

* *Explore* shapes the feature's rationale, outcome, and scope before graph refinement.
* *Refine feature* turns an existing ticket into product-level behavior, use cases, and requirements. Related graph items may carry shared optional `externalId=<id>` metadata for that ticket; this is metadata, not a graph relation.
* *Record change* uses `tspec-new-change` to create one proposed implementation change against approved requirements. `externalId` is optional; detailed software requirements and tasks remain in change refinement.
* *Refine change* defines detailed software requirements and the execution tasks for that particular change. Tasks therefore follow change refinement, not proposal.
* *Accept* is a human gate, not a tool step. Validation enforces it structurally — an accepted change must address a requirement — but a person decides.
* *Apply* implements tasks and records verification evidence against requirements.
* *Archive* verifies conformance independently, then removes only the temporary task checklist.

The relationship is intentionally one-to-many: one external ticket can support several independent changes, and related graph items may share the same `externalId`. Local changes may omit the ID while retaining traceability through `addresses` links to approved requirements.

== The acceptance gate

The `accepted` state is the one state validation polices. Everything upstream (proposed, refined) is free-form drafting; everything downstream (implemented, verified, closed) presumes the proposal was sound.

One structural rule — an accepted change addresses at least one requirement — catches a change with no specification intent, without trying to police semantic quality, which is unreviewable by a linter.

== The tracker boundary

`tspec-track` reads an existing feature ticket or updates only its unique `TSPEC refinement` section after the user approves the exact preview. For GitHub this is a heading; for Jira it is the equivalent ADF section. Everything outside that section is preserved. The workflow does not create or import tickets, update status or backlog position, or set estimates. It does not treat tracker status as graph lifecycle state.

Existing unknown legacy `trackerId` metadata is preserved rather than automatically converted. New external associations use optional shared `externalId` metadata on relevant graph items.

== Temporary vs durable

Tasks live in `tspec/<change-id>/tasks.md` and are deleted when the change closes. Changes, requirements, and decisions are durable and stay in the graph. Approved requirements are immutable: a changed meaning is a new requirement that supersedes the old one, never an edit in place.
