# Add-on-Owned Dependency Readiness

## Goal

Let tracer-spec configure and enforce the graph prerequisites for its workflow activities while keeping Antora Tracer limited to the configurable traceability graph and generic graph access.

Before `tspec` creates an implementation plan for a change, it must be able to require a minimum number of distinct requirements reachable from that change. A requirement may be directly linked or reachable through intermediate items such as use cases. The project may also impose per-item dependency counts, such as requiring each reviewed use case to link to at least one requirement. These are add-on policies, not Tracer graph rules.

## Ownership

- **antora-tracer** owns traceability roles, allowed relationship declarations, graph construction, and generic graph APIs/serialization. Its existing validation checks graph syntax/configuration and relation validity only. This feature adds no dependency matrix, cardinality enforcement, lifecycle gate, activity name, or readiness verification to Tracer.
- **tracer-spec / tspec** owns its dependency matrix, optionality, cardinalities, lifecycle/activity gates, traversal interpretation, readiness results, and missing-item guidance.
- **Other add-ons** may define and enforce different policies against the same generic graph.
- **antora-tracer's write-item skill** authors an item for a declared role. The add-on decides whether and when to invoke it and must honor its confirmation flow.

Graph configuration allows relationships to exist; it does not assert that any must exist or that any workflow step is ready. Matrices generated by Tracer remain reports, not policy enforcement.

## Configuration model

`traceability.yml` remains unchanged for this feature. It continues to define roles and allowed relationships, such as:

```yaml
roles: [change, use_case, requirement]

relations:
  change:
    requirement:
      addresses: { reverse: addressed_by }
    use_case:
      includes: { reverse: included_by }
  use_case:
    requirement:
      leads_to: { reverse: derived_from }
```

This permits the graph edges; it imposes no minimum and triggers no dependency-readiness validation.

`tspec.yml` defines a `dependencyMatrix` that selects which configured graph edges are dependencies for this add-on and any per-parent lifecycle cardinality rules. It separately defines activity prerequisites:

```yaml
dependencyMatrix:
  change:
    addresses:
      requirement: { min: 0 }
    includes:
      use_case: { min: 0 }
  use_case:
    leads_to:
      requirement: { min: 1, at: reviewed }

activities:
  plan:
    for: change
    requires:
      requirement: { min: 1 }
```

In this example, only these three directed edge types participate in `tspec` dependency traversal. `min: 0` means the edge is optional for the source item's lifecycle gate but remains traversable. Each use case must have at least one directly linked requirement when its status is `reviewed`; this rule is evaluated by tspec, not by Tracer. The plan activity requires one distinct requirement reachable through the configured dependency edges. A use case is not required if a directly addressed requirement satisfies the same plan threshold.

The configuration is project-specific and owned by tracer-spec. Its runtime interpretation must validate referenced roles, relations, minima, and states against `traceability.yml` and graph items. There is no fixed required role set.

## Graph access and data flow

Tracer exposes graph data generically. The add-on may use the current public API/CLI or canonical JSON graph output to obtain items and relationships. Existing surfaces include `antora-tracer process --format json` (items and relationships), the generic `query linked <id> <role>` command, and canonical graph snapshots. The generic linked query follows outgoing graph relationships without interpreting add-on rules; it is sufficient only when that traversal semantics matches the add-on policy.

For relation-filtered paths from `tspec.yml`'s dependency matrix, tracer-spec consumes generic items/relationships and performs its own traversal/counting. It does not ask Tracer to load tspec configuration or evaluate its rules. Do not add a Tracer API solely to implement the tracer-spec matrix; if existing generic data surfaces prove inadequate, scope any proposed Tracer addition separately as a policy-neutral graph access capability.

The add-on traversal counts each reachable item ID once, follows only its configured dependency edges, and terminates on cycles. Activity readiness and per-item lifecycle gates are evaluated by tracer-spec against the same graph; they remain distinct rules.

## Runtime behavior

1. `tspec-propose` creates or updates the durable proposal items according to its existing authoring flow, then obtains the graph using the generic Tracer interface.
2. Before writing `tspec/<change-id>/tasks.md`, it evaluates each `activities.plan.requires` target role for the selected change. A target counts if it is reachable through `dependencyMatrix` edges; multiple paths to one ID count once. If a configured minimum is unmet, report observed and required counts and do not create the plan checklist.
3. If missing items should be authored, `tspec-propose` invokes the existing write-item skill for a role already declared by the project. It follows role guidance and explicit confirmation, refreshes/re-reads the graph, then reevaluates readiness before writing tasks.
4. Add-on validation (for example, `tspec-validate`) evaluates any configured per-item lifecycle minima at their named states. A use case missing its requirement may remain a draft; it must meet the rule before it is treated as reviewed/ready according to tracer-spec workflow policy. Tracer itself does not enforce this gate.
5. A proposal may have durable graph records without a plan checklist until plan readiness passes. If readiness is unmet, the agent reports the blocker and available actions; it does not fabricate a plan or silently lower the configured threshold.
6. If the requested scope seems too broad for a single change, `tspec-explore` may recommend splitting into smaller independently implementable changes. The user chooses; the skill never splits or rewrites the change automatically.

Example: a change with no direct `addresses` relationship can satisfy plan readiness through `change --includes--> use_case --leads_to--> requirement`. A direct `addresses` relationship can also satisfy the minimum. With two routes to the same requirement, the count is one. These semantics come entirely from tracer-spec's configuration and evaluator.

## Compatibility and boundaries

- Do not add dependency matrices, cardinality rules, readiness validation, workflow stages, or tracer-spec config loading to Antora Tracer.
- Do not couple Tracer to add-on activity names, configuration keys, or policy formats.
- Do not change Tracer's existing role/relation configuration contract, graph API semantics, JSON output, or snapshots for this feature.
- Keep the existing generated traceability matrices as reporting features, not enforcement rules.
- Do not import OpenSpec's artifact schema, store, or lifecycle. Reuse only the idea of configuring activity prerequisites where useful.
- Do not require use_case, design, or another fixed role unless the project's tracer-spec policy config requires it.
- Do not add automated change splitting, automatic role invention, or a new runtime dependency.
- YAML is runtime input: tracer-spec validates its own `tspec.yml` dependency rules; Tracer validates only its own traceability configuration and graph relations.

## Verification criteria

- Tracer behavior and config remain unchanged by this feature; a graph with declared but absent optional relationships is not rejected for unmet add-on rules.
- Tracer does not load `tspec.yml`, know workflow activity names, or evaluate dependency cardinalities/readiness.
- tracer-spec rejects its own invalid dependency rules (unknown role/relation, invalid minimum, or unknown lifecycle state) with actionable diagnostics.
- A direct requirement and a configured transitive path through a use case can each satisfy the plan threshold.
- Duplicate paths to one requirement count once; two distinct requirement IDs count twice; unconfigured graph relations do not contribute.
- A missing prerequisite blocks only creation of the temporary plan checklist; an optional use case does not block when the requirement threshold is otherwise satisfied.
- A configured per-use-case requirement minimum is checked by tracer-spec at its configured lifecycle state; draft items remain incomplete without creating a Tracer error.
- The evaluator honors write-item confirmation, refreshes graph data after approved writes, and rechecks readiness before creating tasks.
- `tspec-explore` recommends but never applies a scope split.
- No Tracer behavior change or new Tracer API is required unless separate investigation shows generic graph access is inadequate; any such proposal remains policy-neutral and separately reviewed.
