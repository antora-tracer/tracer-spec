= Workflow Overview

== Phases

=== Exploration

An idea or problem is identified.
A Requirements Engineer considers the scope and impact.

=== Proposal

A change is proposed with a description of the intended outcome.

Status: `proposed`

=== Refinement

Use cases describe how stakeholders will interact with or benefit from the change.

Status: `refined`

*Structural requirement:* At least one use case must link to the change.

=== Acceptance

Requirements specify what the system must do.
The change addresses one or more requirements.

Status: `accepted`

*Structural requirement:* The change must address at least one requirement.

=== Decision

Architecture Decision Records capture why decisions were made.
Each ADR leads to or refines a stable design concept.

Status: `adr: accepted`, `design_concept: accepted`

*Structural requirement:* An accepted ADR must lead to at least one design concept.

=== Planning

A temporary change plan is written or generated.
The plan may be revised as understanding evolves.

Location: `plans/CHG-NNN.plan.adoc`

The plan is not a durable traceability artifact.
It is a working document for the implementation team.

=== Implementation

Code, tests, and documentation are created.
Changes reference requirements, ADRs, and design concepts.

Status: `change: implemented`

=== Verification

Tests pass and reviewers approve.
The change is verified to address its requirements.

Status: `change: verified`

=== Closure

The change is complete.
Requirements remain part of the durable project knowledge.
The plan may be archived or discarded.

Status: `change: closed`

== Status policy

=== Declarative states

States are declared in `traceability.yml` as metadata.
Initial policy does not enforce transitions — Git/PR review controls state changes.

=== Structural validation

The workflow validates that:

* A `refined` change has at least one `use_case`.
* An `accepted` change has at least one `requirement`.
* An `accepted` ADR has at least one `design_concept`.

Validation produces warnings, not errors.
Future versions may add transition enforcement if audit requirements demand it.

== Review and authorization

Git pull requests remain the review mechanism.
No separate workflow database or permission layer is introduced initially.
Committers may change item status directly; the workflow configuration documents the intended path.

== Change history

Git provides full history and bisect capability.
Graph snapshots (JSON) may be generated at release boundaries for historical analysis.
